Biomedical graph RAG

Ask the graph. Understand the answer.

RAGnosis is a text-only biomedical assistant. It retrieves related entities from a remote Neo4j Aura knowledge graph, then Cohere writes a follow-up or advice reply from that context.

Open diagnosis Read the architecture

What it does

A chat that looks up the graph before it speaks.

You describe symptoms in the browser. Flask posts that turn, plus the on-page transcript, to POST /chat. The server searches Neo4j Aura, then asks Cohere to reply using the retrieved properties and the conversation so far.

The live production path is keyword retrieval, not vector search. Matching uses Cypher CONTAINS over name, text, description, disease, symptom, title, and canonical_name, limited to five nodes. Embedding fields are stripped before context is sent to the model.

Production

What is deployed

The Render web service is Flask, remote Neo4j Aura, Cohere Chat, and this HTML UI. gunicorn binds 0.0.0.0 and the host-provided PORT. GET /health reports process liveness even when Aura or Cohere is down. /chat returns the real retrieval or generation error instead of a fabricated answer.

This deployment is text chat only. Voice input, speech synthesis, Gradio, image upload, and notebook-only RAG variants are not part of the production path.

About

A retrieval-augmented biomedical assistant, documented as it actually runs.

Medical questions are easy to answer fluently and harder to ground. RAGnosis separates lookup from language: Neo4j Aura supplies a small set of related graph entities, then Cohere writes the response from that retrieved context. The application is informational and is not a substitute for professional diagnosis or treatment.

The problem

Grounding before generation

A language model can produce a fluent medical-sounding answer without being tied to a maintained knowledge source. RAGnosis puts retrieval before generation so the response can be informed by structured biomedical entities when relevant graph context is available.

Why a graph

Structured context

Symptoms, diseases and related biomedical descriptions can be represented as graph entities with properties. The production service queries those properties with Cypher and passes the resulting context to the language model.

Neo4j Aura

Graph retrieval

The production application connects lazily to remote Neo4j Aura. Search uses case-insensitive CONTAINS matching across name, text, description, disease, symptom, title, and canonical_name. At most five matching nodes are returned for a turn.

Embedding fields are stripped from the retrieved context before it is sent to the language model.

Cohere

Language generation

Generation uses Cohere Chat with command-a-03-2025 as the primary model and command-r7b-12-2024 as fallback when the primary model is unavailable.

The API key is supplied through the COHERE_API_KEY environment variable. The application returns an error when generation is unavailable rather than inventing a diagnosis.

Production

The live service is a Flask application hosted on Render. The service runs with gunicorn, connects to the remote Neo4j Aura instance and uses Cohere Chat for generation.

Engineering decisions

Simple production boundary

Secrets are provided through environment variables. The application can start without a live Aura connection. The health endpoint can still report process liveness when dependencies are unavailable. Chat failures are returned to the client rather than replaced with fabricated answers.

Limitations

Production retrieval is keyword/property matching rather than semantic vector search. The context window is intentionally small, with up to five retrieved nodes. Offline repository data should not be assumed to represent the current contents of the live Aura graph.
